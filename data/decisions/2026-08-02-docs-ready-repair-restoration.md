# Captain rulings, 2026-08-02 — Docs Ready, repair, restoration

Given by voice note. Transcribed and read back here so the wording is on the record.

## 1. What Docs Ready means

The captain's definition, and it is better than the one we proposed:

> "What does Docs Ready mean? It means that the skill has already run on it and it's ready for
> manual review and I should be able to just press one button and that one button literally will
> send it off."

**Docs Ready = one click from sending.** Not "some documents exist". Not "a pack row is present".
The reporting skill has already run, everything needed is assembled, a human glances at it, presses
one button, and it goes.

That is the acceptance test for the column. If a card in Docs Ready cannot be sent by a single
button press, it does not belong in Docs Ready.

**And it is per family, never one universal list.** The captain gave each:

- **Physical make-safe** — the make-safe report, the SWMS, the draft invoice, and the email ready to
  go with the email rules applied. One button sends it.
- **Roof report** — validation that the roof report was actually completed on the Prime link. Two
  acceptable channels: a trade confirming they completed the report on the link, **or** the
  deterministic portal reader observing that the Prime form has been filled out. Either satisfies
  it.
- **Assessment report and quote** — the same shape as roof: a mix of the trade channel and the
  deterministic check.

This settles the "who may assert READY" question too. Readiness is not asserted by a person; it is
the state of having everything assembled and sendable. The trade confirmation and the portal reader
are both **evidence inputs**, not authorities that declare readiness.

Note what this rules out: the five-artifact shorthand applied board-wide. A roof job produces no
SecureWorks report, so demanding one would permanently block the roof family.

## 2. Repair

> "For the repair cards, let's just keep it really simple for now and make it just match the whole
> existing system. But we can change that later on."

**Repair takes the existing system's recipe.** Do not invent a separate repair recipe, and do not
park repair as unprocessable. It behaves like the standard flow until the captain revisits it.

This supersedes the earlier recommendation to park it. It also unsticks the scaffolding card
`SWMS-261029`, which was blocked precisely because a repair card could not report or invoice.

## 3. Restoration

> "Restoration is exactly the same as any other job, so it is a different family type."

**Restoration behaves exactly like a standard job and keeps its own family label.** Same recipe as
any other job; the family type is retained for identification, not for different handling.

The separate defect still stands and should be fixed: the one restoration card currently opens the
generic construction screen instead of the make-safe screen, giving it fewer documents and more
buttons that can change things than any other card on the board.

## 4. What this unblocks

- Release 4, canonical family as a real engine input.
- Release 7, Docs Ready authority and pack composition, now defined per family above.
- The repair and restoration recipes, both previously CAPTAIN-UNSET.
- Roughly 19 held items across the four.

Still outstanding: `SWMS-261059`, which is a duplicate-survivor question rather than a stage
question, and the overlay re-anchoring reaffirmation.
