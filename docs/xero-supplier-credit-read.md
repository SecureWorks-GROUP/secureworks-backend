# Supplier-credit evidence reads (TP-07 / TP-01)

`GET ops-api?action=read_xero_settlement_record&record_type=credit_note&record_id=<Xero UUID>` now accepts either Xero credit-note type: `ACCRECCREDIT` (customer) or `ACCPAYCREDIT` (supplier). It returns `ledger_side: receivable|payable` alongside the unchanged raw provider record and provenance. The existing SecureSuite tool uses this same door without new arguments.

This unblocks Bookkeeping's known supplier-credit IDs from AgedPayables, previously rejected with 409 `NOT_ACCREC_SETTLEMENT`. The exact-ID route preserves original dates, updated date, status, lines, allocations and their invoice identities/amounts, remaining credit, currency, tax and payment records. It does not infer which accounting period an allocation belongs to from the credit's document date, or assign a job from a division tag.

The list defaults to receivables, so existing receipt consumers do not silently gain supplier credits in their population. Explicit `ledger_side=payable` with `record_type=credit_note` lists only `ACCPAYCREDIT` records. It returns `ledger_side`, unchanged raw records, provenance and the existing one-page pagination envelope. No mixed-side option is offered. Invalid side/kind combinations are rejected before provider access; a mixed or contradictory provider page is rejected rather than silently filtered. Payment, overpayment and prepayment reads retain their receivables restriction. Wrong/missing/duplicate IDs and unknown types are refused. Existing staff authentication, tenant selection, provider GET, cooldown and provenance behavior are unchanged; no cache/business write, provider POST, new key or permission change is introduced.

A returned supplier credit is original evidence, not permission to apply, backdate or adjust an allocation. No credit nets against cost here, and no bank-statement signoff, payment approval or job cost-close follows from a successful read.

Provider contract: [Xero Credit Notes](https://developer.xero.com/documentation/api/accounting/creditnotes/). Tests execute the actual read function and injected GET-only provider interface, including raw source preservation, customer/supplier separation, invalid identities/types, contradictory invoice side, unchanged default list filtering, explicit supplier selection, pagination boundaries and no database access. ## Supplier-credit population read

`sw_list_xero_settlement_records({record_type: "credit_note", ledger_side: "payable", page: 1, page_size: 100})` uses the same existing authenticated GET route. Follow `next_page` until `end_of_results_observed`; retain provider IDs across pages. A full page only means another may exist; an empty page is not proof that every preceding page was read. `traversal_complete` therefore remains false, and changing provider data can produce page gaps or duplicates. A page bound is not completion. There is no implicit date or status filter: original document date, allocation date, provider status and work period must be considered separately by Bookkeeping. Draft/voided/deleted records, where returned by Xero, are evidence, not allocated costs.

Release backend support before the connector advertises the argument. The old backend rejects it, never falls back to customer credits. The existing exact-ID read remains usable independently. This adds no new authentication scope, key, write action or financial policy. Existing payment/overpayment/prepayment list restrictions are retained. Verify a real supplier page and an exact known credit after authorized release; local fixture-provider tests cannot establish original supplier coverage or financial correctness.

Provider parameter/type contract: [Xero's official OpenAPI definition](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml), `getCreditNotes`: GET `/CreditNotes`, where/order/page/pageSize and ACCPAYCREDIT.
