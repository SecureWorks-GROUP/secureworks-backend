# Dispatch review workbench

Shaun can retain accepted jobs with no order/date/deposit, organise stable requirements into arbitrary groups, review the complete set, capture notes, allocate ordered supply, count physical stock, receive/transfer material, prepare a real unsent PO draft and edit exact email drafts. This is a review workflow. No action invokes purchase authorisation, supplier/customer sends or crew rescheduling.

## HTTP contract

The existing authenticated `ops-api` accepts only office operators (admin/owner/ops_manager JWT or privileged server credentials). JWT organisation and actor come from authentication; request-supplied tenant/actor are ignored. All `dispatch_*` actions have the same office gate. Routine/read-agent credentials remain denied by their existing exhaustive allowlists.

GET actions:
- `dispatch_list?cursor=<uuid>&limit=50`: accepted/unresolved eligible jobs, `next_cursor`, explicit coverage. The SQL view includes accepted quotes independent of job stage and retains post-acceptance-stage jobs with unresolved evidence. Archived/cancelled/deleted jobs are excluded explicitly.
- `dispatch_job?job_id=<uuid>`: `{job,version,source_version,groups,requirements,notes,drafts,movements,allocations,receipts,order_drafts,purchase_orders,documents,communications,media,context_facts,supply_lots,assessment,coverage,live_actions_enabled:false}`.
- `dispatch_supply?kind=po|stock&cursor=...`: existing ordered PO lines across the organisation or audited physical stock counts. Capacity is checked again atomically during allocation.
- `dispatch_communications?scope=job|all&job_id=...&search=...&cursor=...`: captured PO communication records with original job/message/thread provenance. Captured mail is not complete Outlook history.
- `dispatch_outlook_search?mailbox=...&search=...&cursor=...`: actual Microsoft Graph read adapter, using incumbent token/request utility. `DISPATCH_READ_MAILBOXES_BY_ORG` maps tenant UUIDs to an explicit array of readable mailboxes. No configuration means unavailable; it does not default to somebody's mailbox. Exact continuation URL is constrained to the selected mailbox/query, never an arbitrary token-bearing URL. Search is provider-bounded (1000); records remain unlinked until an explicit attribution action. Group conversations require their own source adapter.
- `dispatch_calendar?from=YYYY-MM-DD&to=YYYY-MM-DD`: shared assignment/PO source identities and proposed Dispatch movements, with dated and undated arrays. Staff uses incumbent overlap and cancellation semantics. Per-source bounded coverage is explicit.
- `dispatch_tasks?status=<pending|running|done|failed|deferred|exhausted>&limit=25&offset=0`: visible task/reconcile status for the caller's organisation. Limit defaults to25 and is capped at100. Response includes `items`, `has_more`, `next_offset`, `source_failures`, `source_failures_has_more`, `source_failures_next_offset`, and `live_actions_enabled:false`.
- `dispatch_execution?job_id=<uuid>`: returns up to100 newest held execution actions, capability flags and coverage. The read first expires stale execution leases for the organisation, so `claimed`, `provider_draft_ready` or `sending` actions with a past `lease_until` are returned as `outcome_unknown` rather than active work.

POST `dispatch_command` envelope: `{job_id,expected_version,source_version,request_id:<uuid>,command,payload}`. Returns the refreshed complete aggregate. Reuse the same request ID and exact envelope on uncertain retry; conflicting reuse is rejected. Version/source conflicts return HTTP409.

Commands:
- `group_upsert {id,name,position}`, `group_delete {id}` (unassigns, never deletes requirements).
- `requirement_upsert {id,group_id,description,quantity,unit,specification,source_ref,phase,destination,needed_by,owner}`, `requirement_move {id,group_id}`, `requirement_review {id}`, `set_review {}`. A supplied requirement must reconcile allocations before editing quantities/specs. Scope refresh never overwrites manual rows; source revision changes invalidate review.
- `note_upsert {id,text}`, `note_promote {id,requirement}` (deliberate, single promotion).
- `stock_record {id,description,quantity,unit,location,evidence}` is a recorded physical count, not an inferred inventory row.
- `allocation_upsert {id,requirement_id,supply_id,quantity}`, `allocation_delete {id}`. Stable supply IDs are exactly `po:<uuid>:<line-index>` or `stock:<id>`. Alternate PO spellings such as zero-padded indexes are invalid because they would create separate capacity pools. PO line revision/reordering with outstanding reservations refuses until reconciled. Prepared coverage deducts all organisation-wide reservations against the same PO line, not only this job's allocations. Units must match. Damaged quantities allow replacement allocations without counting unusable goods twice.
- `receipt_upsert {id,allocation_id,usable_quantity,damaged_quantity,location,evidence}`, `receipt_transfer {id,location,evidence,new_id?}`. Move the same counted receipt from yard to destination; never create a duplicate receipt for the same goods. `new_id` is required for any split: partial usable transfer, or retained damaged quantity while moving all usable quantity. Split lineage is returned as `split_from`.
- `order_prepare {id,supplier_name,xero_contact_id,delivery_date,delivery_address,requirement_ids,unit_prices,notes,existing_supply_reviewed:true}`. Current reviewed requirements become lines in an incumbent `purchase_orders` draft within the same transaction. Only the identical Dispatch-owned unsent draft can be edited. Null prices/financial totals remain unknown, never fabricated zero costs. No Xero/provider action occurs.
- `draft_upsert {id,sender,to,cc,subject,body,attachments:[{id,name,source_ref,revision}],po_id,purchase_commitment,thread_id,proposed_delivery_at}`, `draft_review {id}`. Review binds exact content hash/source, including explicit `purchase_commitment` classification. Missing classification requires purchase authority; linking any PO always requires it. Editing strips prior review. PO association must belong to job. Review confers no live execution authority.
- `movement_upsert {id,title,from_location,to_location,date,time,requirement_ids}` saves a proposal only.
- `communication_link {id,communication_id,source_job_id,reason}` verifies original captured-mail job/tenant. Native Graph results retain mailbox custody; a provider-message attribution adapter is a remaining integration item.

POST `dispatch_assess` uses the same optimistic envelope. POST `dispatch_trigger {job_ids:[up to25]}` creates deduplicated source+plan-version tasks; an omitted `job_ids` advances a durable eligible-job cursor by at most25 and wraps to recover missed or late changes. Incumbent `business_events` also enqueue external job changes, excluding exact Dispatch self-derived plan events through the shared SQL predicate. Current assessments do not enqueue themselves again. POST `dispatch_run {}` leases up to10, persists assessed/superseded/failed/deferred/exhausted results, and retries failures with bounded automatic attempts. Lease tokens and lease expiry fence stale workers. POST `dispatch_retry_task {job_id,request_id,source_version?,plan_version?,reason}` is an authenticated operator retry; `source_version` and `plan_version` must be supplied together for an existing task, or both omitted for a failed source. Retries are idempotently audited by `request_id` and use the authenticated actor. `scripts/dispatch/worker.disabled.json` and its runner provide an opt-in bounded schedule; the checked-in configuration is disabled and no scheduler is installed or activated. Current job-context source is read through `current_job_context_facts` plus incumbent visibility rules, never re-ingested. General context remains visible in job reads; only exact Dispatch self-projection is excluded from action-critical source hashing and event enqueue echo. Company-context contract remains CIO-owned and not yet release-proven.

## Review amendments and held execution

PO supply lifecycle follows incumbent ordered states: submitted/authorised/sent/confirmed/delivered/billed; quote_requested/draft/approved do not prove an order. Missing physical units refuse allocation (a quantity-one lump-sum fence PO is not one physical fence kit). PO-wide line snapshot fencing prevents a line reorder from creating duplicate capacity at a new array index.

Order preparation accepts `quantities:{[requirementId]:number}` and defaults to the uncovered amount after allocation and other prepared drafts, supporting partial orders and multiple suppliers. `requirement_reconcile {...fields,reason}` retains custody through explicit scope changes and exposes excess/unit mismatch. Metadata changes stay editable after receipt. `context_review {}` acknowledges the exact source/fact revision. `receipt_transfer` supports optional `quantity`; `new_id` is mandatory whenever the transfer creates a conserved split, including retained damage, and retry uses the same caller-minted split UUID.

Execution is now implemented as a separate held action lifecycle, not an unsupported command. Configured Captain user IDs may POST `dispatch_draft_approve` (normal optimistic envelope, payload `{id,approval_id,content_hash,communications_approved:true,purchase_approved:true}` for supplier commitment). Review and approval remain separate. Exact approval survives only matching content/source. POST `dispatch_execute {job_id,draft_id,approval_id}` claims one durable action identity with `lease_token` and `lease_until` for a two-minute lease, prepares a provider draft, records provider identity before send, requires the current exact token for `dispatch_begin_send`, and records `accepted_not_delivered` or `outcome_unknown`. POST `dispatch_execution_readback {approval_id}` performs read-only provider reconciliation. GET `dispatch_execution?job_id` supplies actions, coverage and capabilities after normalising expired active leases to `outcome_unknown`.

Both environment `DISPATCH_SEND_RELEASED=true` and tenant `dispatch_release_controls.communications_enabled=true` are required; defaults remain held. `DISPATCH_APPROVER_USER_IDS` has no default approver. Tests inject a fake provider; no actual send is made. Native Outlook new-mail adapter reuses existing Graph token/request, mailbox verification, SES delivery guard and attachment download restrictions, hashes actual attachment bytes against reviewed revisions, and retains immutable provider draft IDs. Provider acceptance never establishes delivery. Captured Resend thread IDs cannot be used as native Outlook message IDs; native/captured reply execution remains a stated integration gap, not a fake reply.

Execution SQL wire used by the handler:

| RPC | Purpose |
| --- | --- |
| `dispatch_claim_execution(p_org,p_job,p_draft,p_approval,p_hash,p_source)` | Creates or returns the durable approval action; new claims start `claimed` with a two-minute `lease_token` / `lease_until`. Held tenants return `status:'held'` without claiming. |
| `dispatch_record_execution_progress(p_org,p_action,p_expected_status,p_expected_receipt,p_expected_source,p_lease_token,p_status,p_receipt,p_error)` | CAS progress writer for prepare/send outcomes. Active provider draft progress refreshes the two-minute lease; terminal or unknown outcomes clear it. |
| `dispatch_begin_send(p_org,p_action,p_lease_token)` | Exact-token send cutoff. Revalidates release, approval, content and source, then moves the action to `sending` under the current lease. |
| `dispatch_get_execution(p_org,p_action)` | Read path for one action; expires stale active leases to `outcome_unknown` before returning. |
| `dispatch_expire_execution_leases(p_org,p_action)` | Shared lease expiry used by claim, read, list, progress and readback paths. |
| `dispatch_record_execution_readback(p_org,p_action,p_expected_status,p_expected_receipt,p_expected_source,p_readback)` | CAS readback writer. Exact verified sent identity moves `sending`/`outcome_unknown` to `accepted_not_delivered`; inconclusive evidence keeps the held recovery state. |

Joint browser fixture: `tests/dispatch/local_server.ts` runs the actual production handler/reducer/SQL with a narrow local PostgreSQL query transport. `browser_fixture.sql` seeds unmistakable synthetic records. It omits real JWT verification, provider calls and PostgREST projection fidelity. It is bound to loopback ports55581/55582 and the fixed `dispatch_ui` database. Browser writes and reloads preserve actual persisted state; never deploy this fixture. The HTTP rollback test overlays the reviewed migration and copies one bounded saved Dispatch aggregate from the held schema; it proves that aggregate's PO/draft/note state, not complete live schema parity.

The final execution preflight repeats full approval/content/source/release validation after provider preparation and immediately before the native send request. SQL `dispatch_begin_send(p_org,p_action,p_lease_token)` fences the current exact action token; a missing, old or mismatched token is stale and cannot start or refresh send authority. A sending draft cannot be edited/reapproved through Dispatch while in flight. Revocation is available with `draft_revoke {id,reason}` before the send cutoff. Proven pre-provider failures produce `not_sent`; uncertain preparation/send failures retain native receipt and remain `outcome_unknown` with no automatic resend. Read-only provider readback uses exact immutable provider identity and a SQL compare-and-set transition from `sending` or `outcome_unknown` to `accepted_not_delivered` when the same provider message is verified sent; delivery remains unknown. Inconclusive readback, including still-draft evidence or provider lookup failure, remains held for recovery and does not imply delivery. Progress and readback writes compare expected status, receipt and source version; progress also requires the execution lease token. A late execution result cannot overwrite a terminal readback or a newer action state.

Attachments are resolved server-side from selected current-job document/media IDs; browser URLs/timestamps are not authoritative. The resolver fetches through existing guarded storage transport and binds actual SHA256 bytes into the returned draft descriptor. Native Outlook replies are supported when the exact Graph message ID, changeKey, conversation and explicit job-link reason are supplied and reverified. Provider recipients/body must exactly match reviewed fields; arbitrary captured Resend thread IDs remain unsupported as native mailbox identity. The native reply adapter preserves provider draft identity on preparation failure.

Shared-context integration: each human command atomically appends `business_events` event `dispatch.plan.changed`, source `ops-api`, correlation ID=request UUID, job ID=canonical UUID, payload contract `dispatch-context/v1` with plan/source versions and review-state snapshot. Metadata identifies `dispatch_plans`/org/job/version and `human_working_state`, `provider_action:false`. Assessment-only writes do not emit self-feeding ingestion events. The producer uses incumbent `match_status:matched` / `match_method:direct_job_id` attribution after validating the canonical job/organisation. Tenant gates now apply before shared event serialization through job detail, dossier and brain reads. `persist_luna_context_revision` consumes that persisted source snapshot under its existing job/source/fact contract; this branch does not duplicate ingestion or rewrite CIO ownership. Event delivery failure rolls back the human change rather than silently hiding it from the shared stream.

Context echo protection is part of `dispatch-context/v1`: CIO must preserve event metadata `derivation:{owner:'dispatch',event_id,plan_version}` plus canonical org/job/request/plan/source IDs and singleton source-event identity under the projected fact's `provenance.derivation`. A single SQL predicate owns Dispatch self-projection classification for source reads and event enqueue skipping; owner tag alone is insufficient. Full projected state remains available in `context_facts`; `upstream_context_facts` and the action-critical source hash exclude only exact Dispatch-derived output. General, malformed or mixed lineage context remains upstream. Current SQL proof is contract-shaped against local fixtures; the actual frozen CIO projector artifact is still pending because the candidate artifact was not accepted.

Cancelled, deleted, missing or changed supply cannot establish coverage; original receipt allocation and transfer/split history remain bound. A physical stock count can be zero. Job/context/calendar reads use a 999th sentinel below the configured 1000-row REST cap and expose at most998 rows per source, reporting incomplete coverage instead of accepting truncation. ## Frozen material suitability wire

`dispatch_command` now accepts `allocation_confirm_suitability` with payload `{id:<allocation UUID>,reason:<nonempty text>,evidence:<nonempty text>}` under the existing exact `job_id`, `expected_version`, `source_version`, and `request_id` envelope. Request-supplied revisions or suitability flags are ignored. The server binds the current physical requirement revision and verified supply revision, and records `suitability_confirmation:{requirement_revision,supply_revision,source_version,reason,evidence,actor,at}`. Missing, cancelled, changed or unverified supply cannot be confirmed.

Each returned requirement has `physical_revision`, derived from description, specification and unit; quantity-only changes preserve that identity. Each allocation has `requirement_revision`, `supply_revision`, `current_supply_revision`, `suitability_status:current|stale`, and nullable `suitability_obligation`. A physical specification change retains allocations, reservations and receipt custody but removes their contribution to material/site coverage. Generic requirement, set and context review do not restore suitability. Explicit evidence-backed compatibility confirmation or replacement allocation supplies the missing coverage. Historical unsuitable receipts remain visible after replacement; they do not duplicate ready coverage. Existing allocations without a recorded revision require explicit confirmation before contributing coverage.

`context_review` now requires available, complete general and upstream context reads, matching assessment's coverage boundary. `dispatch_supply` accepts only omitted `kind`, `kind=po`, and `kind=stock`; all other explicit values are rejected. Outlook mailbox failures thrown as `GraphProviderError` return `coverage.available:false` and `complete:false`, including permission failures and throttling.
