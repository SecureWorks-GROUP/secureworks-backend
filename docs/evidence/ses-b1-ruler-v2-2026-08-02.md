**Date:** 2026-08-02
**Scope:** `supabase/functions/ops-api/makesafe_evidence_requirements.ts` and its
suites. Code only. **Zero production writes** — the ruler is pure by
construction and every production read here went through the Management API with
`read_only: true`.
**Authority:** `data/decisions/2026-08-01-po-wo-invoice-ruling.md` (Captain,
verbatim), routed by plan v2 §D "Batch 1" under the §D.0 write-safety rules.
**Ruler version:** `ses-evidence-requirements/c1-unlinked-invoice-v3` →
`ses-evidence-requirements/c1-wo-floor-po-optional-v4`.

---

## 1. The rulings

1. **Work order: required on EVERY card, no exceptions.** "We have nothing to
   invoice against without a work order."
2. **Purchase order: NOT required.** Expected to usually exist, but absence is
   not a failure. This re-answers `Q_PO_FLOOR`, superseding the earlier quick
   "of course every card needs a po" — which the Captain clarified was about
   work orders.
3. **SWMS: required only for MLB make-safes.**

## 2. What changed in the table

| Cell | Before | After |
|---|---|---|
| `po`, all 7 families × all 7 stages (49 cells) | REQUIRED | **OPTIONAL** |
| `builder_wo_doc`, 5 sealed families at `completed` and `archive` (10 cells) | `question("terminal_evidence")` | **REQUIRED** |
| everything else | — | unchanged |

`po` stays **observed**. It is optional, not dropped: every reading still emits
`observed_present`, `observed_count` and the measured `detail`, so a purchase
order remains visible on the card whenever one exists. It is simply never a
gate, at any stage, in any family.

Two boundaries the ruling does **not** cross, deliberately:

- `builder_wo_doc` at **`cancelled`** stays `question("cancelled_floor")`. What
  a cancelled card must retain is a separate open Captain question, and this
  ruling did not name it. (`cancelled` is outside the `active-v1` population
  anyway, so it moves no measured number either way.)
- `builder_wo_doc` throughout **repair and restoration** stays open under those
  families' recipe questions. The ruling promotes the cells the draft left open
  under `terminal_evidence`; an unsealed recipe is a different kind of open, and
  sealing one by code change is exactly what the ruler's rule 1 forbids.

## 3. The supersession is recorded, not absorbed

`SesCaptainQuestionResolution` gained an optional `supersedes` chain, and
`Q_PO_FLOOR.resolution` now carries the current ruling with the overturned one
kept verbatim beneath it: its date, what it did to the table while it governed
(including its measured board effect — 359 required-misses, 364 fails), the date
it was superseded, and the Captain's reason. The resolved-question mechanism
exists so a ruling is recorded and never silently absorbed; a ruling that
*replaces* another has to be recorded the same way, or a measurement taken under
the old one stops being attributable. Asserted by
`the superseded PO floor is recorded, not erased`.

`Q_TERMINAL_EVIDENCE` stays OPEN. Its draft text names the work order, but the
ruling answered only that clause; the report, photo, SWMS and legacy-orphan
columns are still unresolved, and the question text is kept verbatim with a note
rather than rewritten.

## 4. SWMS: verified as zero code change

Confirmed true, as plan v2 C.11 predicted. The ruler's cells are family × stage
and carry **no builder identity**, so "MLB make-safes only" cannot be expressed
in this table at all. The builder-aware rule already lives, sealed, in
`ses_family_matrix.ts:229-234`:

```
MLB      -> always
AJS/AJBR -> builder_waiver_unless_hrcw
everyone else, and report-only families -> hrcw_only
```

That is exactly the C.11 reading — *MLB always; everyone else only when the work
is genuinely high-risk construction work*. So nothing was encoded here, and
`Q_REPORT_ONLY_SWMS` stays **OPEN** pending C.11: flattening the
high-risk-construction-work trigger to N-A by builder identity is a
work-health-and-safety call, not a paperwork preference, and it is not this
batch's to make. Pinned by
`SWMS is untouched: the MLB rule is builder-scoped and lives elsewhere`, which
also asserts no SWMS cell is REQUIRED in any family at any stage.
